# Employees Take Revenge — technical overview

How the game works and how it is built. Written 2026-10-21 from the source of the project (`Assets/Scripts`, `Assets/Editor`, `ProjectSettings`, `Packages`) and the project's own hand-off log (`DEVELOPER_NOTES.md`); every number and name below was read from the code or from that log, not recalled. Where this document says "the owner" it means the game's author, whose requests (quoted in the code's comments) set the rules. File names are given so any claim can be checked; the longer history of why things are the way they are is in `DEVELOPER_NOTES.md`.

**A note on the outline this was written against.** It assumed a stack that this project does not use: there is no FMOD, no Mirror/Photon, no Odin serializer, no Supabase/PlayFab (or any backend, database, analytics or cloud save), no object-pool framework and no persistent HUD minimap. What the game has instead is described in each section (Unity Netcode for GameObjects over a custom Steam transport, audio generated in code, `PlayerPrefs` for the handful of settings, small purpose-built pools, and a "Nav map" on an in-world security computer). Section 6 lists the places where the project is thin or unproven.

## 0. The game in one page

*Employees Take Revenge* (the project folder and repo are still called `BuildingEscape`; the lobby tag is `employees-take-revenge`) is a cooperative heist game for up to five players. The party starts in the **Loading Docks** (a safe hub with a black-market vendor), rides a service elevator up through a 13-storey office tower (the 13th floor is the boss's), and on each floor must carry enough loot back to the elevator to meet that floor's **quota** while security officers patrol, call for backup, pin and arrest players. Between groups of three floors the team returns to the docks to sell loot, buy weapons and armour, and pay to get arrested teammates back. The demo currently ends at floor 6 (`TowerRules.DemoLastFloor`, the owner's 2026-10-23 change from floor 4); the code for the whole tower, including a boss floor, exists.

**The one idea that shapes the architecture:** the whole game is *one* Unity scene (`Greybox`) into which every floor is **generated at run time from a seed**, identically on every machine, and then thrown away when the elevator moves on. Because floors are pure functions of `(run seed, floor number)`, a multiplayer session never ships floor geometry over the network; it ships a seed, a handful of requests and events, and a 15 Hz stream of moving things.

```
Boot scene ──► Menu scene (lobby) ──► Greybox scene (the run)
 persistent      3D lobby stage          the Loading Docks and every floor,
 "Net" object    + toon menus            generated into it one at a time
 (NetworkManager, SteamService,
  transports, NetSession)

authority:   each player body = its own machine (client-authoritative transform)
             everything else  = the host (guards, loot physics, rules, money, the vendor)
             clients send Request*; the host validates and answers with an event (RPC) or state (NetworkVariable)
```

| AI | `NavMeshAgent` guards on a NavMesh **baked at run time** per floor (AI Navigation 2.0.5, `NavMeshSurface`) |

## 1. Core infrastructure and architecture

### 1.1 The tech stack and the tooling around it

**Packages** (`Packages/manifest.json`): `com.unity.netcode.gameobjects` 2.13.1, `com.unity.transport` 2.7.4, `com.rlabrecque.steamworks.net` (git package), `com.unity.ai.navigation` 2.0.5, `com.unity.shadergraph` 17.0.4 (the Synty materials are shader graphs), `com.unity.toonshader` 0.11.0-preview (installed; the characters use one Standard-shader material with the pack's colour atlas, because the packs' own URP shaders render pink in the Built-in pipeline — `ToonCharacterFactory`), plus Unity's default modules. `STEAMWORKS_NET` is the scripting define for the standalone player.

**Build.** `Assets/Editor/DemoBuild.cs` (menu *Employees Take Revenge → Build demo (Windows)*, or batch mode with `-executeMethod BuildingEscape.EditorTools.DemoBuild.Build -buildOutput <folder>`) builds Windows x64 from the scenes ticked in Build Settings and copies `steam_appid.txt` next to the exe. `-buildBackend il2cpp` switches the scripting backend (IL2CPP builds exist so the game's code is not a plain .NET assembly). Builds go to `Builds/` (git-ignored); there are about 70 dated builds in it, `Playtest_2026-10-20b` being the newest as of this writing.

**Editor-side scaffolding.** `Assets/Editor` also holds the *catalog builders* (`OfficeCatalogBuilder`, `CharacterCatalogBuilder`, `WeaponCatalogBuilder`, `CityCatalogBuilder`, `AudioCatalogBuilder`, `FloorSurfaceCatalogBuilder`) which scan the art packs once and write ScriptableObject catalogs into `Assets/Resources` (the game loads them with `Resources.Load`), `NetSceneBuilder` (builds the Boot and Menu scenes, the player and `RunSync` prefabs and the network prefab list from code, so they can be rebuilt), `FloorPreviewWindow` (generates a floor outside Play Mode), and `RenderAudit` (finds magenta/error-shader renderers).

**How it is tested** is the subject of section 5: pure-C# rule tests, batch-mode Play Mode scenarios, two-process multiplayer scenarios over loopback, and a self-playing autopilot inside built players.

### 1.2 How the code is organised

The code follows three habits that make the rest of this document easier to read.

1. **Rules are separated from scene behaviour.** Anything that is arithmetic or a decision table lives in a static class or a small struct with **no `UnityEngine` types**, so it can be compiled and tested outside Unity: `CustodyRules`, `GuardRules`, `TowerRules`, `GunRules`, `GuardLoadouts`, `HackSession`/`HackRules`, `SafeRules`, `IntroRules`, `VoiceRules`, `LootScanRules`, `DoorLogic`/`DoorGeometry`, `AimMath`, `PingRules`, `StaminaMeter`, `NavView`/`NavMotion`/`NavMapRules`, the whole floor planner (`OfficePlanner`, `FloorShape`, `LootPlan`, `ValuablePlan`, `AfterHours`, `DirectionSigns`), and the DSP/music code (`Dsp`, `SynthRandom`, `ProceduralSound`, `ProceduralMusic`, `MusicPlan`). The `MonoBehaviour`s (`GuardAI`, `HeistManager`, `Vendor`, `OutpostController`, …) feed them numbers and apply the answers. About 650 checks run against these rule classes in a single batch-mode call.
2. **Big systems are split with `partial class`.** `FloorGenerator` is 14 files (`.Interior`, `.Outpost`, `.Doors`, `.Dock`, `.Surfaces`, `.Glass`, `.AfterHours`, `.Valuables`, `.RoomNumbers`, `.Signs`, `.Speakers`, …); `RunSync` is 13 (`.State`, `.Snapshots`, `.Requests`, `.Events`, `.Guns`, `.Outpost`, `.Intro`, `.Pa`, `.Pvp`, `.Darts`, `.Ping`, …); `OfficePlanner` is 4; `ComputerScreen` 2.
3. **Systems install themselves.** Most cross-cutting services are a `MonoBehaviour` with a static `Instance` that creates itself from a `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` hook and calls `DontDestroyOnLoad` — `Crosshair`, `PingSystem`, `VoiceChat`, `MusicDirector`, `StaminaHud`, `ComputerScreen` (and `GunFx`, on the first shot). Every static is reset in a `SubsystemRegistration` hook so the Editor's "domain reload off" mode does not leak state between Play sessions.

Almost nothing is authored in the Unity editor. **Content is built in code**: the lobby stage and the dock behind it, the vendor's trailer, the elevators, the guards' capsule-and-nose bodies (dressed afterwards by `GuardVisual`), the boss's office, the city outside the windows (roughly 900 towers in nine merged meshes), glow textures, the signs' dot-matrix text (`DotText`), even the sound effects. The three `.unity` scene files are tiny (7–31 KB).

### 1.3 Scenes and the lifetime of a session

* **`Boot`** holds one persistent `Net` object: `NetworkManager`, `UnityTransport` (loopback test mode), `SteamNetworkTransport`, `SteamService` (Steam API lifetime and callback pump), `NetSession` (the state machine that turns "play with friends" into a running session) and `BootLoader`, which loads `Menu` one frame later. `Application.runInBackground` is forced on (a host who alt-tabs must not freeze the team or stop the voice).
* **`Menu`** has a camera and a `LobbyMenu`; `LobbyStage` builds a 3D stage where the party's characters stand on pads (driven by `NetSession.Roster`), in front of `LobbyDock`, a primitive-built Loading Docks. Customising a character, hosting, joining by code or invite, the friends list and settings are all IMGUI pages of `LobbyMenu`.
* **`Greybox`** is the run. It contains a directional light, `HeistManager` (+ `HeistHud`), a `Tower` object with `FloorGenerator` and `TowerManager`, the main camera with `CameraFollow`, and one offline player capsule marked `OfflinePlayerOnly` (it removes itself in a networked run, which spawns one `NetPlayer` per client instead — the networked player prefab is that same capsule plus `NetworkObject`, `OwnerNetworkTransform` and `NetPlayer`); everything else is created at run time. NGO's scene management loads it on every machine when the host presses Start. (`GreyboxBuilder` and `NetSceneBuilder` in `Assets/Editor` can rebuild these scenes from code.)
* **PLAY SOLO** (and pressing Play on `Greybox` in the Editor) runs the same scene with **no network session at all** — `NetRole.Simulates` is true, `NetRole.Synced` is false, there is no `RunSync`. Every gameplay script is written to work in three situations — offline, host, remote client — which is why so many methods begin with `if (Net.NetRole.IsRemoteClient) return;` or branch on `NetRole.Synced`. Any feature has to be tested on both start paths, and the test harness does.

`NetSession` states: `Offline → Connecting → InLobby → StartingRun → InRun`. Hosting on Steam creates a Steam lobby (public, code-only or friends-only; five-character codes from an alphabet without 0/O/1/I), starts the NGO host on the Steam transport, and publishes lobby data (`game`, `ver` = `<Application.version>/<ProtocolVersion>`, `code`, `state`, per-member `ready` and `look`). A client joins through the lobby, compares the version string, then connects P2P to the lobby owner's SteamID. The host's **connection-approval callback** re-checks the version, the player cap (`NetConst.MaxPlayers` = 5) and — on Steam — that the connecting Steam identity (taken from the transport, never from the payload) is a member of the lobby (`JoinPolicy.Evaluate`, a pure function). `NetConst.ProtocolVersion` is a string bumped every time a wire message or a rule changes in a way that would desynchronise old and new builds (it is at "27"); its comment is a one-line changelog from protocol 2 to 27.

### 1.4 State management and persistence

**What is saved between sessions — very little.** There is no save file, no profile, no progression, no backend. The complete list of persisted data is seven `PlayerPrefs` keys (plus an Editor-only switch for the dev test menu):

| Key | Holds |
|---|---|
| `OvertimeEscape.Appearance` | the player's chosen character look (a serialised `PlayerAppearance` string) |
| `OvertimeEscape.MasterVolume`, `…MusicVolume`, `…VoiceVolume` | volume sliders |
| `OvertimeEscape.MouseSensitivity` | look speed |
| `OvertimeEscape.VoiceMode` | open mic / push-to-talk / off |
| `OvertimeEscape.Crosshair` | reticle on/off |

(The key prefix is a leftover from the working title "Overtime Escape".) Steam lobby metadata carries each member's ready flag and character look so friends see each other on the lobby stage; it lives only as long as the lobby does. There is no use of Steam Stats, Achievements, Cloud or any web request in the code.

**A run is ephemeral and lives in a few objects**, all reset when a run starts:

* `HeistManager` — the run's ledger: `Phase` (`Lobby, Heist, FloorComplete, Won, Failed, Hub`), `Floor`, `Quota`, `Banked`, `Lost`, `RunTotal`, spendable `Cash`, the repeating-backup clock, the radio-jam timer, the custody transitions (below).
* `TowerManager` — which level is being built, where the elevator resumes (`ResumeLevel`), the run's seeds, and the build/rescue logic.
* `RunUnlocks` (guns and armour brought back to the docks, which unlock their ammunition and armour at the vendor), `SafeIntel` (what the notes have taught the party about the floors' safes), `PvpBoard` (the basement PVP room's leaderboard).
* Per-player state on the player object: `Backpack` (the pack), `Stamina`, `PvpFighter` health, `WobblyPlayer.Custody`, the gun's `GunMagazine` (rounds and reserve travel with the gun item).

**In a networked run the host owns that state and mirrors it.** `RunSync.State.cs` publishes a block of `NetworkVariable`s each frame (phase, floor, quota, banked, cash, time, backup countdown, elevator flags, destination, doors that backup comes out of, unlock mask, outpost bits, PA state) and `ClientApplyState` writes them into the client's own `HeistManager` through `ApplyNet`. Two details make this safe across floor changes:

* **The epoch.** Every floor has a one-byte `RunSync.Epoch`. The host bumps it in the same RPC that tells everyone to build the next floor (`LoadLevelRpc`), snapshots and floor-bound messages are tagged with it, and a machine that is still building the previous floor (a slow one) ignores state and events whose epoch is not its own. `vReadyEpoch` tells clients when the host has *finished* the new floor, so values that still describe the old one are not applied. The outpost's three state bits are even packed as `(epoch << 8) | bits` in a single `ushort`.
* **A load queue.** If a second "build floor N" arrives while one is being built, `TowerManager.NetLoadLevel` queues it; two floors are never generated at once, and a floor whose build throws still clears `Loading` so the elevator cannot die for the rest of the run (`LoadFloor` steps the build coroutine by hand inside a `try`).

**Identity of things.** Every pickup and guard registers with `Net.NetIds` in `Awake`, which hands out integers in creation order. Because the floor generator creates the same objects in the same order on every machine, the ids match without ever being sent; things created later (a vendor purchase, a backup guard, a clip a guard drops) are announced by the host with the id to use (`NetIds.PendingId`). `NetIds.Reset()` is called at the start of every floor, and after a floor is built the host publishes `NetIds.Checksum()` and the object count; a client that disagrees logs `[NetSync] DESYNC`.

### 1.5 Networking

**Topology.** A listen server: one player is the host and also a player. Up to five players (`NetConst.MaxPlayers`). There is no dedicated server, no host migration (if the host leaves, every client is told "The host left the game" and returns to the menu) and no joining a run in progress (`JoinPolicy` answers `RunStarted`).

**Transport.** `SteamNetworkTransport` is a custom `Unity.Netcode.NetworkTransport` over **ISteamNetworkingSockets** with Steam's relay network: the host opens a P2P listen socket on its SteamID (no port forwarding, no server of ours), clients `ConnectP2P` to it. It maps Netcode client ids to Steam connection handles (id 0 is the server, clients count up from 1), turns a connection away when the host already has `MaxConnections` (accepted ones plus ones still being accepted) or that Steam account is already connected (`ShouldAccept` — anybody who knows the host's SteamID can try to connect, so strangers must not fill it up; lobby membership is checked afterwards in Netcode's approval callback), and enforces a **per-client receive budget** of a 1 MB burst refilling at 128 KB/s, so a modified client cannot flood the host. Timeouts are raised to 25 s for the first relay connection and 15 s once connected, because the first relay hop can take several seconds. Two other modes exist for development: `UnityTransport` on loopback ("local" mode with a roster message instead of a Steam lobby), and, in Editor/development builds only, the Steam transport over loopback IP (Steam refuses a P2P connection to your own account, so two copies on one PC test the real transport this way).

**Authority.** Two rules:

* **A player's body belongs to its own machine.** `OwnerNetworkTransform` is a `NetworkTransform` whose `OnIsServerAuthoritative()` returns false (half-float precision, only Y rotation, interpolated). The owner runs the normal single-player scripts (`WobblyPlayer`, `VoiceNoise`); on every other machine the same capsule is a *puppet*: kinematic, input scripts off, animation derived from how far it moved (`NetPlayer.Update`). `Backpack`, `PlayerGrab`, `MeleeController` and `GunController` keep running on puppets because they hold shared state, but read input only for the player the camera follows (`Viewed`).
* **Everything else belongs to the host**: guards, loot physics, money, the vendor, doors, locks, safes, the elevator, who is pinned. Offline or host (`NetRole.Simulates`) runs the rules; a remote client only simulates its own body and shows what the host sends. Guards on a client are *puppets* (`GuardAI.IsPuppet`: the `NavMeshAgent` is disabled, `Update` returns at once); loose items are made kinematic.

**The request → validate → event pattern** (`RunSync.Requests.cs`, `RunSync.Events.cs`). A gameplay script calls a `Request*` method. On the host that runs the check directly; on a client it is an `[Rpc(SendTo.Server)]`. The host method (`HostStore`, `HostGrab`, `HostDoor`, `HostBuy`, …) first asks `PlayerOf(senderId)`, which also applies a **token-bucket rate limit** (`RateLimiter`, pure C#: 60 requests burst, 40 a second, per client), then checks everything it can: the player exists and is not in custody, the item exists, is enabled and is not held, the player is near enough (`ReachCheck` 4.5 m, deliberately generous because the sender's view is a moment old), numbers are finite, the epoch matches. Only then does it announce the result with an `[Rpc(SendTo.ClientsAndHost)]` event — and **every machine, the host included, applies the event through the same method** (`StoredRpc → Backpack.ApplyStored`, `GrabbedRpc → PlayerGrab.ApplyGrab`, `DoorSetRpc → DoorManager.NetSet`, …), so there is one code path and the host's own copy cannot drift from the clients'. Requests state an *intent*, not a toggle — a door request says "open" or "shut", so two players pressing E in the same moment cannot undo each other. Features add their own limits on top: guns (`GunMuzzleSlack`, the gun's own fire interval ×0.8 with a small burst allowance), melee hits (0.35 s apart, within 3.6 m), the noise report (within 8 m of the sender's body, loudness capped at 40), pings (a burst of 3, then 1.5/s, within 90 m), voice (a burst of 100, then 70 packets/s).

**State and streams.**

* *State*: a block of host-written `NetworkVariable`s (section 1.4) mirrored into the client's managers; a floor-tagged `ushort` for the outpost's lock/alarm/safe bits.
* *Snapshots*: the host sends the position and rotation of every moving **pickup and guard** about **15 times a second** as unreliable-sequenced custom messages (`be.snap`). An entry is 17 bytes — id (2), kind (1: for a guard his packed loadout), position as three `int16` at 1/64 m (±512 m), rotation in 4 bytes (*smallest-three* quaternion compression: two bits say which component was dropped, 10 bits each for the others), state, call progress, flags (dead / calling / armed / eating), speed — and only entries that changed (moved more than 2 cm, turned more than 0.7°, or changed state) are sent, plus a 2-second refresh for everything. At most 60 entries go in a message. Nothing is sent when the host is alone. A client glides each puppet to its target with an exponential ease (`k = 1 − e^(−18·dt)`), and **leaves a puppet alone once it is within 2 mm** — writing a transform every frame for every loot item on a floor makes the physics engine treat all of them as moving.
* *Events*: reliable RPCs for things that happened (stored, dropped, equipped, grabbed, released, consumed, shattered, spawned item/guard/key/clip, a guard fired, a blast, toasts, door changes; custody is the exception: it rides on `NetworkVariable`s of the player object).
* *Voice* and *noise reports* use their own paths (sections 4.1 and 2.3).

**Floor changes** are the delicate part, and are handled by (a) the epoch, (b) the load queue and (c) the **checksum**, all described in 1.4, plus the way cargo is treated: loot left in the elevator car rides to the next floor, so the host names the items in the car (`CargoIds`) inside the same RPC that starts the build, every machine lifts exactly those items out of the old floor, re-parents them under `TowerManager`, builds the new floor, and `PlaceCargo` sets them down at the back of the new car and calls `Pickup.RenewNetId()` so they get new ids in the same order everywhere.

**Disconnects.** A player who drops out puts their pack down where they stood (`NetPlayer.DropPackWhereTheyStood`, run on every machine; the host's physics settles it); `RunSync.expected` shrinks so nobody waits for a player who is gone; `HeistManager.CheckTeamDown` re-evaluates "is anybody still free"; the voice and pin state clean up. A client that cannot reach the host leaves with a plain-words reason (`NetSession.OnClientDisconnected` rewrites Netcode's technical text).

**What is *not* there**, honestly: no client-side prediction of the world (a client sees guards and loot about one snapshot behind), no lag compensation of shots beyond a 1 m aim forgiveness for guards (`RunSync.Forgiven`, section 2.4), no anti-cheat or encryption of its own, and movement is trusted to the owner, so a modified client could move itself anywhere. The notes file host-side gaps of this kind under "fine for friends, not for a public build" (`DEVELOPER_NOTES.md`, section 6).

### 1.6 Memory and performance strategy

The code was written with a frame budget in mind rather than profiled against one — the notes are candid that nothing here came from a profiler session ("Not applied for lack of a profiler: static batching of the floor's boxes, instancing of repeated props"). What is done:

* **Pooling where objects would otherwise churn.** `GameAudio` plays every one-shot on a **fixed pool of 32 `AudioSource`s** built once (steal-the-oldest, but never a sound younger than 0.15 s), so footsteps, keys and radios — dozens a second — never create or destroy an object. `GunFx` pools the shot's visuals: **6 muzzle flashes (each with its own point light), 14 tracers (`LineRenderer`), 12 sparks and 14 ejected cartridge cases per case model**, reused round-robin. `SoundBank` makes each synthesised clip once per session and keeps it (`DontUnloadUnusedAsset`). There is **no general object-pool framework**; `LootShards` bursts (22 cube shards) and one-off effects still allocate, which is acceptable at their rate.
* **No-allocation queries on hot paths.** Physics queries use `RaycastNonAlloc` / `OverlapSphereNonAlloc` into static buffers sized for the worst case measured (`Ballistics` 192 hits because a rifle's line crosses dozens of colliders and the non-alloc call returns the *first* hits it finds, not the nearest — they are sorted by distance afterwards; `Pickup` 256 colliders; `Crosshair` 48; the vision cone 64). `NetIds` is a `Dictionary<int, Component>`; the pickup search reuses a `HashSet` and a `List`; the camera-rig lookups are throttled to twice a second.
* **Immediate-mode UI without garbage.** The first HUD allocated a native `GUIStyle` per label per event; the audit replaced that with cached styles and **Repaint-only drawing** (`HudText`, `HudStyles`, `HudTheme`: rounded rectangles come from `GUI.DrawTexture` with border radii, so the HUD has no textures of its own). The house rule is "never `new GUIStyle` inside `OnGUI`".
* **Spreading work over frames and threads.** Guard vision cones are meshes rebuilt every **second** frame per guard with the guards taking turns (`FanEvery`), and fade out for guards the camera cannot see; the AI's door look-ahead scans about 10 times a second, not every frame (`DoorManager.ScanEvery`); synthesised sounds are **prewarmed one per call** during the first frames so the first use mid-heist never hitches (`SoundBank.PrewarmNext`); each floor's **music track is rendered on a worker thread** (`Task.Run(ProceduralMusic…)`) as soon as the floor loads, long before backup can be called; the DSP code is plain C# for that reason.
* **Culling and merging.** `PropCuller` switches the *renderers* of far rooms' furniture off (every 0.35 s, with 8 m of hysteresis, `propDrawDistance` 60 m) so "a 5,000-prop floor stays light"; floors and carpets are **one merged mesh per surface** with no collider (the NavMesh ignores them); partitions are boxes; furniture prefabs are measured once and kept as inactive templates that are cloned; a floor's couple of hundred real (pixel) lights exist but **only the ≤ 8 nearest the camera are enabled at any moment** (`FloorLights`, rescanned every 0.25 s, with fades), since a pixel light costs time on everything it touches. Floor meshes, scenery meshes and materials made at run time are tracked in `OwnedObjects` and freed when the floor goes (a destroyed GameObject does not free its meshes or materials).
* **Network economy.** Delta-compressed, quantised, 17-byte snapshots at 15 Hz; voice that is *not relayed* to listeners out of earshot and *not decoded* below an audibility threshold; state mirrored as a handful of ints, not messages.
* **GC settings.** Incremental GC is on in the project settings. Nothing in the game calls `GC.Collect`; the built-player autopilot (section 5) *measures* instead: at every stop it records average, 95th-percentile and worst frame time, the number of generation-0 collections and the managed heap size.

Measured on the owner's machine (RTX 3060 Ti, 1920×1080, Ultra; from the QA runs recorded in `DEVELOPER_NOTES.md`): about **230 fps** in the docks, **60–107 fps** in the first seconds after a floor is built (the elevator view, with the scenery and ceiling lights drawn), about 235 fps walking a floor, and roughly 40–55 fps per window with two built players on one PC. The city outside the windows is about 870 towers in nine meshes built in about 10 ms after the first floor.

## 2. Gameplay mechanics and frameworks

### 2.1 The player: a physics body, a camera, a stamina bar

**The body.** `WobblyPlayer` drives a `Rigidbody` capsule with **forces**, not a character controller: `AddForce(moveInput × moveForce, Acceleration)` while the flat speed is under `maxSpeed` (5 m/s; sprint ×1.6 for as long as the `StaminaMeter` allows; crouch ×0.55), a *self-righting torque* (`KeepUpright`) that gives the clumsy "wobbly" look, and a tilt cap of 9° so sideways walking does not tip it over. Hard impacts (relative speed over 9 m/s) trip the player (`Stumble`), which is also what a guard's bullet or a blast does. Jumping is an impulse and needs the ground ray (`CheckGrounded`, a ray from the capsule's middle to just past the feet; the old version reached too short and never grounded). Crouching lowers the capsule (collider height ×0.65, feet kept in place), squashes the model a little (the rigs have no crouch clip) and makes footsteps quieter. The body is moved only by its own machine; to *place* it (an elevator spawn, a rescue) one must use `WobblyPlayer.TeleportTo` / `NetPlayer.PlaceAt`, because writing `transform.position` is undone by the next physics step when the rigidbody is interpolated (the cause of an early "players fall out of the map" bug, recorded as a house rule). `TowerManager` also rescues any local player below y = −30 m by putting them back in the elevator.

**Stamina** is a pure class (`StaminaMeter`: drain 16/s while sprinting, regenerate 12/s after a 1 s breather, "winded" until a quarter of the bar is back) wrapped by a `MonoBehaviour` and drawn by `StaminaHud`.

**Noise.** Footsteps feed the `NoiseBus` (section 2.3): 3 m walking, 8 m sprinting, 0.9 m crouched, every 0.5 / 0.28 / 0.75 s; a hidden player makes none.

**The camera** (`CameraFollow`) is an over-the-shoulder rig (2.6 m behind, 0.45 m to the right, pitch −35°…60°) with collision pushing it in, plus a smooth zoom to **first person** (mouse wheel up, `P`, or Ctrl+Up; the eye is 0.62 m above the capsule centre and the camera's near plane is brought in to 4 cm so a gun's sights can sit a hand's width from the lens, and the character's own body and arms are hidden or re-posed for it: `ShowArms`/`ShowBody`, the first-person arm shader). Free-look orbits the camera without turning the body; down a sniper scope the field of view narrows by the rifle's magnification and the mouse turns the view proportionally less. The dart game and spectating borrow the rig: `LimitAim` constrains yaw/pitch to a cone around a target, `spectate` makes the camera orbit another body while *everything that asks who is "viewed"* (the pack, the keys, the HUD) still looks at the player's own body, so a knocked-out player watching a teammate cannot act through them.

**Characters.** `PlayerVisual` dresses the capsule from a `CharacterLook` (saved choice, or by slot) through `PartyCharacterFactory` (the colourful Party characters, animated by an Animator controller with triggers) or `ToonCharacterFactory` (Tiny Toon people, no controller: `CharacterAnimator`'s **clip mode** blends idle/walk/run/knocked-down/slash/stun clips in a small `PlayableGraph`). Everything else talks to the same few methods (`Locomote`, `Fall`, `Stun`, `Recover`, `Jump`, `PlaySlash`) and does not care which rig it is. On a humanoid clip-mode rig the weapons' Blender animations (`PistolAnimation`, `WeaponAnimation`; set up as humanoid clips by `Editor/WeaponAnimationSetup`) go on top in a layer mixer over the upper body: a gun held (`GunPose`: the raise, the aim, a shot; a long gun in both hands), a pistol's reload, a melee weapon held ready or swung (`MeleePose`); `HeldGun` and `MeleeController` call them every frame and put the weapon in the hand where the Blender file holds it. A teammate's look travels as a short string (`PlayerAppearance`) in the Steam lobby and in a `NetworkVariable<FixedString64Bytes>` on the player.

### 2.2 The state machines, and how they avoid soft-locks

There is no single "game state machine"; there are several small, independent ones, each owned by the machine that is authoritative for it.

**(a) Player custody — `Free → Pinned → Busted` (`CustodyState`, rules in the pure `CustodyRules`).** Custody is decided only on the host (`HeistManager`) and *applied everywhere* through the same method (`WobblyPlayer.ApplyCustody`, which a client receives from three `NetworkVariable`s on the player object: state, seconds left, the level they were busted on).

| Transition | Trigger | Guard against a soft-lock |
|---|---|---|
| Free → Pinned | an officer within 1.6 m with an unobstructed line (`HasReach`: a ray chest-to-chest that fixed geometry — but not a crate or a body — blocks) calls `HeistManager.Pin` | `CanPin` requires `Free` and `now ≥ PinImmuneUntil`; god-mode / not in a heist / not the host → refused, so the officer keeps chasing |
| Pinned → Free | the officer holding them is hit, punched, stunned or put down (`ReleaseHold(freeThem: true)` → `FreePinned`) | a freed player is immune to pinning for **3 s**, so the officer cannot re-pin at once |
| Pinned → Busted | `PinSeconds` (12 s) run out (`TickCustody`) | if the holder is gone or dead the player is freed instead of waiting for a timer that no one is running |
| Busted → Free | the vendor's buy-back (`ReleaseBusted`; price = 300 + 50 × the level they were busted on) | also freed with a 3 s immunity |
| anything → Busted | a shotgun or sniper hit from an armed officer (`Blast`: the owner's rule that those two *eliminate* a player for the floor) | |
| whole team → run over | no player is `Free` (`CustodyRules.TeamDown`) → `HeistPhase.Failed` | re-checked on a disconnect, so a free player who leaves cannot leave the others pinned for ever |

While in custody the body lies where it fell (`HoldDown`: damped velocity, a torque that tips it onto its back), cannot walk/jump/hide/grab/swing/shoot/use doors, panels, the vendor or computers (each of those scripts checks `InCustody`, and the host re-checks it on every request), carries nothing (`PlayerGrab.Release`), and is skipped by guards (`CanSee` returns false), by bullets (`Ballistics` passes over a body in custody) and by the elevator ("everyone aboard" ignores busted players). A new floor clears all pins (`ClearPins`) but busted players stay busted until bought back.

**(b) The guard — `GuardState { Patrol, Investigate, Chase, Stunned, Calling, Pinning }`** (`GuardAI`, rules in pure `GuardRules`). Run by the host (offline: by the machine); a puppet only displays a state the host sent.

| From | To | When |
|---|---|---|
| Patrol | Investigate | a noise within `loudness × hearingMultiplier`, a bullet that did not kill him while he was not busy (he turns to the shooter), or a PA alert |
| Investigate | Patrol | he has waited 3 s at the place he went to look |
| Patrol, Investigate | **Calling** | a free player has been in his cone for `0.15 + 0.12 × distance` seconds (a quarter of that for a backup officer); or a bullet that did not kill him |
| Calling | **Chase** | the 2 s call ends (backup is called) with a free player still in view; a shot officer goes after whoever shot him |
| Calling | Investigate | the player was out of view for more than 0.3 s (`CancelCall`: no backup) |
| Chase | **Pinning** | a free player within 1.6 m, nothing solid between them, and `HeistManager.Pin` accepts |
| Chase | Investigate | no free player in his cone for 5 s (`LoseChase`), or his target was taken and nobody else is in view |
| Pinning | Investigate | the pin ended (freed by a blow, busted, bought back) — `EndHold` |
| Patrol (unarmed, not on a post) | eating | 1.5 % chance at a patrol stop: a donut break of 6.5 s that any noise, sighting or blow ends |
| any state | **Stunned** | a melee blow, a punch or a thrown item (bat 3 s, crowbar 4 s, hatchet 6 s); when he gets up he radios (Calling) |
| any state | **Dead** | damage reaches `hitsToKill`: stays `Stunned` for ever with his colliders off; `GuardCorpse` sinks the body after 15 s |

Notes on the details that matter: a **bullet never knocks a guard over** — it subtracts damage (the gun's `guardHits` less what his shield absorbs: light 75 %, medium 50 %, heavy 30 % of the damage gets through; a piercing round would ignore it) and, if it does not kill, makes him stop and radio for backup for 2 s (`BeginShotCall`; killing him in time cancels the call — the owner's rule of 2026-10-21); a **melee blow** knocks him over for the weapon's time and cuts a call in progress; the boss takes melee as one of thirty hits. The loop in `Update` is `TickCall()`, then the state's own update, then `ScanForPlayers()` for any state that is not Chase/Calling/Pinning. Each state sets the `NavMeshAgent` explicitly (`isStopped`, `speed`, `SetDestination`) so that no state can inherit a stale destination from another. A patrol that makes no progress for 3 s (a door locked from the security computer) gives up on that leg (`stuckFor`), so a locked door cannot freeze a guard for ever.

**(c) The run — `HeistPhase { Lobby, Heist, FloorComplete, Won, Failed, Hub }`** (`HeistManager`). `StartFloor` sets `Hub` for the docks or `Heist` for an office floor; banking enough value (`Banked ≥ Quota`) moves `Heist → FloorComplete`, which unlocks the elevator; the boss floor is won by `BossDefeated`; `Failed` comes from the whole team being down (or an optional timer). `TowerRules` (pure) is the elevator's rulebook: the team may climb three floors, must then go back to the docks (3, 6, 9, 12), cannot go up before the quota is met, cannot leave a floor for the docks before it either (the owner's rule of 2026-10-17), and floor 12 holds a key (carried by one guard) to a hidden elevator to the boss on 13.

**(d) Smaller machines** with the same discipline of "pure logic + a thin driver": `DoorLogic` (a struct: open fraction, want-open, linger time; a door that is closing re-opens if something is in the doorway; the caller gives the door a collider only once it `IsShut`, so a door in motion can never knock anybody over), `HackSession` (`Intro → Prompt → Won | Lost | Cancelled`), `GunMagazine` (fire/reload/dry), `NetSession` (section 1.3), the cinematic's `Waiting → Playing → Done`.

### 2.3 How guards perceive: sight, sound, radios and backup

**Sight** (`GuardAI.CanSee`, `GuardRules.InVision`, drawn by `GuardVision`). The cone is a flat fan `sightAngle` 65° each side and `sightRange` 14 m, plus a **long, narrow beam** straight ahead (±9°, up to 2.4 × the range ≈ 34 m, smoothly widening: `RangeAt`) so a long hallway is dangerous; a *hidden* player is seen only within 1.5 m; anyone within 0.4 m is seen whichever way the guard faces. Inside the fan the guard must also have a clear view (`GuardAI.HasClearView` -> `GuardRules.SeesBody`): from his eyes (`GuardAI.EyePoint`, 1.8 m above the floor) a line level with them to where the player stands, and a line to the player's head, chest or knees (lower when he crouches), must not meet a wall, a door or a fixed piece of furniture (`GuardSight.Blocks`). The lines end at the player, and loose objects, carried loot, other players and other officers never block them, nor do trigger volumes (so standing in a hide zone does not make you invisible). Seeing is not noticing: each guard keeps a **notice meter** (0 to 1) per player in `ScanForPlayers` (`GuardRules.NoticeStep`). While the player is in his sight it fills at `1 / (0.15 + 0.12 x distance)` of the meter per second, the distance being the flat one the cone is measured in: about 2 per second at 3 m, 0.55 at 14 m and 0.24 at the 34 m end of the long beam, so a player who stays in sight is always noticed in the end, only slower the further away he is (a backup officer fills it four times as fast). Out of sight it holds for 0.25 s (so a flickering line does not undo it) and then drains at twice the speed it fills. Each meter belongs to its guard: nothing depends on how many guards there are. Noticing starts a **call**, not a chase: the guard stops for `callSeconds` (2 s) and radios; the player must stay in view (with a 0.3 s grace for a flickering ray) or the call is dropped and the guard just investigates where they were. A chase lasts as long as *any* free player stays in his cone and ends 5 s after the last glimpse. The vision cone is the *same geometry the guard uses* — a translucent mesh on the floor, cut short by walls (a view ray per segment, `Clip`; the rays are `GuardRules.ConeRay`, start at the same eyes and are stopped by the same things as his sight check), coloured yellow/orange/red by state, so players read the danger directly — and it is hidden while the camera cannot see the guard (the owner: players must not learn that a guard is around a corner).

**Sound** (`NoiseBus`). A static event bus: anything loud calls `NoiseBus.Emit(position, loudness, source)` — footsteps, a stumble (10 m), a thrown mug, loot shattering (30 m) or hitting something hard (up to 25 m), a gunshot (the pew 45 m, 12 m silenced; the rifle 55; the shotgun 60; the sniper 85), a melee hit, a voice (3–30 m by how loud the speaker is, section 4.1). Every guard subscribes (`OnNoise`) and compares the distance with `loudness × hearingMultiplier`; a guard who is calling, chasing, pinning or stunned ignores it, and a guard with a `noticeGate` (the guard on duty in an outpost) is deaf to anything outside his room. On a remote client `Emit` does not run the guards (they are puppets): it sends `RequestNoise` to the host, which accepts it only if it is finite, at most 8 m from the sender's body and no louder than 40.

**Doors.** Guards open sliding doors *for themselves*: every 0.1 s `DoorManager` asks each walking guard for his route (`GuardAI.GetRoute`: his position and the remaining corners of his agent's path, or a straight-ahead guess for a client's puppet) and `DoorGeometry.RouteEnters` (Liang–Barsky clipping of each leg against the doorway's zone) says whether he will walk through it within the next 0.9 s, so the door opens in time and closes behind him; a guard who merely walks past opens nothing.

**Backup** (`HeistManager.CallBackup`). When a call completes, the first one on a floor sends two officers *and starts a clock*: another officer arrives every 30 s on floor 1, shortening in equal steps to 12 s on floor 12 and above (`CustodyRules.BackupInterval`), until the floor ends, with at most 24 guards alive. Officers do not spawn in the outpost: they arrive through **the guards' own elevator** in the corner cell opposite the players' elevator, or one of **two stairwells** in the other corners (`FloorGenerator.OrderEntries`: doors at least 12 m from every free player first, in random order, the door the previous call began with moved to the back), then `Dispatch` to where the team is. The alarm (a failed lock hack) calls backup the same way. The outpost's alarm panel that used to call it off was removed; a *stand-down* function remains in `HeistManager`. The hallway **loudspeakers** (`PaRules`: one every ~13 m along corridors, at most 48, each a bit in a `ulong`) are a player tool: a player signed in at the outpost's computer can hold V to speak into them, and any officer within 22 m of a live speaker drops what he is doing and rushes to the outpost for 12 s (`PaAlert`) — a way to pull guards away from teammates.

### 2.4 Combat and hit registration

**Everything is a ray; there are no projectile objects.** Guns are *hitscan*; this is why nothing in the game pools bullets.

`Ballistics.Trace(origin, direction, range, shooter, hitsPlayers)` is the only bullet physics: a `RaycastNonAlloc` into a 192-entry buffer, sorted by distance, then walked nearest-first, skipping the shooter's own colliders, skipping loose pickups (a mug on a desk does not stop a bullet), skipping a guard who is already dead (his standing hitbox must not shield someone behind him — and since 2026-10-21 his colliders are switched off anyway), and applying the *team rule*: **a player's bullet passes through teammates and stops at guards, the training dummy, walls, desks and doors; a guard's bullet passes through other guards and stops at free players**. A ray never reports a collider it *starts inside*, and the muzzle is only half a metre from the shooter, so a guard standing so close that the muzzle is inside his hitbox used to be flown straight through; `Trace` now checks an `OverlapSphere` at the origin first (found by QA on 2026-10-21).

**The shot, locally** (`GunController.Shoot`): the aim point is the camera's centre ray cast from the player's own depth (so a wall behind the player does not count); the muzzle's line to that point is traced. Two details come from QA of the "attack does not connect although it should" report: if the crosshair is on a guard but the *muzzle's* line is blocked by a cubicle panel or a desk edge that the camera's line clears, the bullet leaves the **camera's** line instead (the tracer is still drawn from the muzzle); and a shotgun's pellets each get their own spread from a **seed shared with the host** (`GunRules.PelletSeed(seed, i)`), so every machine draws the same pellets. Flash, tracer, sound and a *guess* at the hit sound happen at once on the shooter's machine.

**The shot, authoritatively.** Offline, `Land` applies the result. In a networked run the shooter's machine sends `RequestGunShot(origin, direction, guardIdSeen, seed)`; the host (`HostGunShot`) verifies the player has that gun equipped, is not in custody, that the muzzle is within 4 m of the player's body, and that they are not firing faster than the gun's interval ×0.8 (with a 0.15 s burst allowance for packets that arrive bunched), then **re-traces every pellet itself**, applies the damage (`BulletHitHost`), emits the gunshot noise, and announces `PlayerShotRpc(slot, endPoint, result, seed)` so the other machines draw the shot in the shooter's hand. Because the guard has moved since the shooter's picture of him was drawn, `Forgiven` accepts a hit on the guard the shooter *saw in his sights* if that guard is within 1 m of the line and nothing solid is between — a small lag compensation, not a rewind.

**Melee** is a timed overlap: after the swing's `hitDelay` (0.22 s with the old slash clip; with a weapon's Blender swing, `WeaponAnimation`, the moment the clip's weapon is at its fastest - the clip is played in the weapon's cooldown, so the crowbar lands at 0.36 s, the bat at 0.32 s, the hatchet at 0.40 s) `MeleeController.Hit` does an `OverlapSphere` (radius 1.4 m) centred 1.2 m ahead along the crosshair direction, and for each *distinct* thing in it (a `seen` set) applies the weapon's effect — a guard is knocked over for the weapon's time, the dummy and (in the PVP room only) a rival lose health, a loose object is shoved. A client's swing on a guard is a request the host checks (`HostGuardHit`: within 3.6 m, 0.35 s apart). Punches (empty hands) are the same with a smaller zone and a shorter stun that frees a pinned friend but never counts towards a knock-out.

**Guns as data.** `RangedWeapon.Specs` is a table (`Pew, Smg, Rifle, Shotgun, Sniper`: damage, `guardHits`, noise, silenced noise, magazine, spare clips, fire interval, reload, range, spread, pellets, kick, hold style, sound set, unlock floor, ammunition name and price). The `Kind` enum order is **the wire format** ("add new kinds at the end": it is a byte in a vendor product, a safe's contents and a guard's packed loadout). A gun is an ordinary `Pickup` that goes in the pack; its rounds live in a `GunMagazine` on the item, so dropping and picking it up again keeps them. A silencer and a red-dot sight are attached models, allowed by gun class (`TakesSilencer`, `TakesRedDot`).

**Armed guards** (`GuardGun`, `GuardLoadouts`, `ArmedGuards`). A guard's loadout is a gun kind plus a shield tier, planned per floor from a ladder (pistols with a light shield from floor 3, SMGs from 5, shotguns with a heavy shield from 6, rifles with a medium shield from 8, snipers with none from 10; shares of armed guards grow with the floor) by a random generator **of its own**, seeded from the floor, so adding armed guards never changes the maze or the loot. In a chase an armed guard stops when he sees a free player inside his gun's engagement window (the pistol: between 3 and 22 m; every gun has its own row in `GuardLoadouts.Tuning`), takes about half a second (less on higher floors: `GunRules.GuardTempo`) to aim, fires single shots or bursts into a cone that widens with distance, reloads, and runs at the player to grab him when he is closer than the window. A hit stumbles a player for 1.8 s (a vest shortens it), except a shotgun or sniper hit, which blows the player up and busts them for the floor (`HeistManager.Blast`, announced to every machine so each plays the effect). The host's loadout rides in the guard's snapshot byte (bit 0 "I am a guard", bits 1–2 shield, bits 3–5 gun kind), and a client's `GuardGun` only *shows* the gun and the shots the host announces (`GuardShotRpc`).

### 2.5 Items, the pack and the vendor

**One item model.** Everything a player can pick up is a `Pickup` (a weight, a label, a bank value, a `NetId`). Treasures add `HeavyLoot` (value × integrity, `lifters` = how many players are needed, a physics mass of `lifters × 6 kg`, fragility and a hit cap of 45 so no single bump destroys it; a piece that falls out of the world is put back where it last stood safe; a piece that its carriers outrun is brought to them), weapons add `RangedWeapon` / `MeleeWeapon`, spare clips `AmmoClip`, armour `ArmourItem`, throwables `Throwable`. The pack (`Backpack`) is a `List<Pickup>` with a weight limit (20 kg, shown in pounds); stored items are **switched off and re-parented under the player** (`ApplyStored`: `SetActive(false)`), so they ride along into the elevator and the host's snapshot skips them ("in a backpack").

**Carrying (Q)** is physical: `PlayerGrab` holds a rigidbody to a hand point with a damped spring (`carryForce` 40, damping 12, acceleration clamped to 70 m/s²) and a heavy treasure moves only when `Holders ≥ lifters`; two or three players' hand points average, the piece is not solid to its carriers while held, turns slowly (angular damping 6) and is speed-limited to 9 m/s so it cannot be whipped through a wall. Only the host moves it; clients see it through snapshots. The reachability of a treasure for two or three is a *level-generation* rule, section 3.4.

**Duplicate and ghost items** are prevented by construction rather than by a lookup structure: an item is one `GameObject` with one `NetId`; `ApplyStored` returns early if the list already contains it; `HostStore` refuses an item that is held, inactive or being carried by someone; a purchase spawns *one* object on the host and announces it with its id; a sale destroys it on the host and announces the id (`ConsumedRpc`) so clients destroy their copy. The vendor's catalogue is a static `Product[]`, bought **by index** (one byte on the wire), re-validated on the host every time (the buyer must be standing at the counter, the item must be on offer *now* — `OnOffer` gates the pew by the floor the party has finished, ammunition by the guns found and brought back, armour by tiers brought back —, there must be cash, room in the pack, no second gun, no second armour piece), and the money lives only in `HeistManager.Cash`.

**Banking and the quota.** Loot dropped inside the elevator car's trigger volume is banked by `ElevatorExtraction.AutoBank` once it has *settled* (not held, speed under 2 m/s, for `settleSeconds`): the host adds its current value to `Banked` and the run total, announces a toast, destroys it and tells clients. The quota starts at $4,300 doubled by the owner's `QuotaMultiplier`, rises with the floor along a formula in `TowerRules.QuotaFor`, and is capped at 60 % of the value that is actually lying on the floor so it can always be met. Loot that the party leaves in the car rides to the next floor. Back in the docks, the vendor buys loot at 70 % of its *current* value (a damaged piece is worth less) and surplus banked above the quota is paid out as cash when the team rides down.

### 2.6 The guard outposts: a lock, a computer, safes and a loudspeaker

Every office floor has a **guard outpost** (a dark-walled room with a one-way window, planned in `OfficePlanner.Outpost`). It is the game's puzzle layer, and almost all of its content is *derived from the run seed by hashing*, never from the floor's random numbers (so it cannot disturb the maze or loot) — `SafeRules.Hash(seed, a, b)` is a well-mixed 32-bit integer hash, and "does this floor have a safe, what is its 4-digit code, does its note give the code, which room is it in, what does it hold" are all functions of `(run seed, floor, salt)`. That lets an outpost on floor 2 hold a note about a safe on floor 5 *before floor 5 exists*, and lets every machine agree without a message.

* **The lock** (`OutpostController`, `HackPanel`, `HackSession`): press E at the keypad and play a quick hack — four different keys from W/A/S/D, one second each, shown one at a time. A win opens the door; a miss shorts the lock, sounds the alarm for 14 s and calls backup. The result is a *request*; the host checks the player is within 6.5 m of the keypad and sets the state, which reaches everyone as three bits in the epoch-tagged `ushort`.
* **The guard on duty** stands inside and is blind and deaf to everything outside his room (`noticeGate`); the players must knock him out before they are noticed.
* **The computer** (`ComputerScreen`, E on it): a log-in whose answer is on a post-it stuck to the monitor, then tabs — *Safes* (the room and, usually, the code of this floor's safes and nothing about what is inside; what is learned goes into the journal), *Nav* (the floor plan, section 4.3) and *Hacked* (a door terminal: type a room number — or `lock 507` / `507 unlock` — and that room's doors switch the other way, a request the host judges and applies for everybody; `SECURITY` names the outpost's own door, which the terminal can lock so hard that officers cannot open it either; V held works the PA). The screen is purely local (every player logs in for themselves); anything that changes the world is a request.
* **The safes** (`FloorSafe`, `SafePanel`): one on floors 1–2 (cash worth half the quota), up to four from floor 7 (a pistol, a long gun standing in a taller safe, armour, a watch, a spare clip — each an item of its own, created dormant at build time so ids match, and switched on when the safe opens). The right code opens it; a crowbar pries it open noisily and snaps 35 % of the time; a wrong code locks the keypad out for 1.5 s. Safe attempts are requests judged by the host (`SafeReply`).

### 2.7 Smaller systems worth knowing

* **Loot scanner** (hold Z): a pulse races over the floor of the *room you stand in* (28 m/s, following walls), marks every valuable lying in that room only (a mark is a diamond and a label seen through furniture, glowing green/blue/gold by worth, red for weapons), repeats every 2.4 s while held. Purely local: every machine has the same loot in the same places, so nothing is sent.
* **Ping** (middle mouse, added 2026-10-21): the crosshair's target — a lootable item, consumable, weapon/armour or door — gets a marker the whole team sees through walls for 8 s (`PingSystem`, `PingRules`, `RunSync.Ping.cs`; the pinger's machine shows it at once and asks the host, which checks the sender, a rate limit and that the point is within 90 m of the sender's body before announcing it to all).
* **The dock radio** (`Scripts/Radio/`: `DockRadio`, `RadioState`, `RadioRules`, `RadioCatalog`; `Hud/RadioScreen`; `Net/RunSync.Radio`): the POLYGON Construction radio on two stacked boxes in the corner east of the vending machines plays one of three stations (Midnight Mode vol.1, the Energy Hard Rock demos, Urban Jazz; `Resources/RadioCatalog`, made by Employees Take Revenge > Setup Dock Radio, which streams the tracks compressed). A station is its tracks in an order shuffled from a seed, looped, and every station runs on one clock for the whole run (switching only changes which is heard, so a station switched back to - or the radio after a floor - is further on); what plays is worked out on every machine from the station, the moment the radio's clock started (on the session's shared clock, `NetworkManager.ServerTime`) and the seed, which the host publishes with the run state - so the team hears the same song at the same second with nothing sent per track. E on it opens a close-up of the radio (a camera rendering to a texture) with its eight buttons where they are on the model; the first three are the stations, the fourth the power, the fifth and sixth the volume (10 steps; on/off and the volume are published with the station), and a client's click is a request the host only takes from someone at the radio. The speaker is 3D at the music volume: full up to 4 m, then its own fall-off curve to 0.4 at the doorway to the elevator room's half of the docks (19 m) and to nothing 6 m past it.
* **The basement PVP room and darts** (`Pvp`, `PvpBoard`, `DartBoard`, `DartsRules`): inside a room in the docks, blows and bullets take health between players and a knock-out is a few seconds (the host decides and tells everyone the health); a dart board at the end of the hallway holds the player at the throw line with the camera's aim limited to a cone, the thrower's machine reports each dart's score and the host tells everybody.
* **Journal and checklist** (`FloorChecklist`, `SafeIntel`): what the notes have taught the team, and a per-floor list of what is still lying about, counted once the floor has settled.

## 3. Level design and spatial management

### 3.1 Vertical structure: one scene, floors that are built and thrown away

There are **no per-floor scenes, no additive loading, no asynchronous scene streaming and no pre-authored levels**. The tower is a *sequence of generated floors in one scene*. `TowerRules` fixes the shape — level 0 is the **Loading Docks** (the hub), levels 1–13 are office floors (13 is the boss floor), the team climbs in groups of three (3, 6, 9, 12) and must return to the docks after each, floor 12 holds a key to a hidden elevator to 13 — and `TowerManager` carries it out.

What "the elevator ride" is technically (`TowerManager.BuildFloor`, run as a coroutine on *every* machine when the host sends `LoadLevelRpc(level, cargoIds, resume, epoch)`):

1. Everyone releases whatever they are carrying (`PlayerGrab.Release`), and the items named as **cargo** (loot left in the car) are lifted out and re-parented under `TowerManager`, so they survive the old floor.
2. The team's bodies are **held still** (`HoldTeam`: kinematic — nobody falls while there is no floor under them).
3. `FloorGenerator.Clear()` destroys the old floor's root object (`Kill`: `DestroyImmediate` in edit mode, `Destroy` in play), and the coroutine **yields one frame** so the old geometry and its NavMesh are gone before the next bake.
4. `FloorGenerator.Generate(floor, baseSeed + floor × 7919)` builds the new floor **synchronously, in one call** — walls, interior, scenery, NavMesh bake, doors, loot, guards, outpost (3.2). It is not time-sliced; the hitch is hidden because the players are in a closed car with the doors shut (the elevator sealed, the lounge music playing, `MusicDirector` keeping it for 5 s after the ride) and held still.
5. `PlaceTeam` puts every player in the new car (spread by slot, in `NetPlayer.Ordered()` order so every machine arranges the team identically), `PlaceCargo` sets the cargo down in two rows at the back and renews its network ids, `HeistManager.StartFloor` resets the ledger, and the host calls `MarkFloorReady()` and `PublishChecksum()`.
6. `ReleaseTeam` lets the bodies go. If another load is already queued (a slow machine fell behind), they stay held until that one is built too.

The **elevator is a real shaft**: the players' car is always cell (0, 0), the guards' car the opposite corner, the two stairwells the other two corners — the same cells on every floor, "like a real shaft", so the party can learn the building. The car is a walled room with sliding doors, a panel of lit floor buttons and a GO button (host-validated, section 2.2c) and a mirror (`PlanarMirror`, a camera that renders the car from the other side of the mirror plane into a `RenderTexture` with `ElevatorMirror.shader`).

### 3.2 The floor generation pipeline

`FloorGenerator.Generate` (the main file is about 1,100 lines; the rest of the class is in 13 partial files) is the single entry point. In order:

1. **Reset and seed.** `NetIds.Reset()`, `new System.Random(seed)`, a `Floor_N` root object. Content that must not depend on the floor's random numbers uses its own streams (below).
2. **Shape.** `SizeOfFloor` turns a design target — a full sweep should take about **7 minutes** at an assumed effective team speed of 3.5 m/s — into a grid: for the settings stored in the scene that is 42 rooms' worth of walking, laid out as **8 × 5 cells of 18 m = 144 m × 90 m** (`rows = round(√(rooms / 1.5))`, `cols = round(rooms / rows)`). The basement is 2 × 1 cells (every wall has a door); the boss floor is a 3 × 2 open arena. `FloorShape.Maze` carves an office floor's maze: a **depth-first spanning tree** from the elevator cell choosing among unvisited neighbours with `rng.Next`, plus extra doorways with probability `loopChance` (0.12) to make loops, with the elevator cell always open to both neighbours. `FloorShape` is pure and is also used to *ask about a floor that has not been built* (below).
3. **Shell and elevators.** Outer walls (with windows on office floors), the elevator room (and, on floor 12, the hidden hallway with the locked back door and the boss elevator), then — after the interior — the guards' elevator and the stairwells (small walled rooms with sliding steel doors; their steps and signs have no colliders). Guards must never wander into a shut car: the players' car and the hidden hallway carry `NavMeshModifierVolume` keep-outs ("not walkable"), and the guards' car and the stairwells are built *before* the bake with their doors open, so their doorways are on the NavMesh, then shut afterwards (`Snap(false)`), while `InGuardShaft` keeps random wander points out of them.
4. **The plan (`PlanInterior`).** `OfficePlanner.Build(PlanInput)` is **pure C#** and returns a `Layout`: rooms (`RoomInfo`: theme, kind, bounds, doors), wall boxes, furniture `Piece`s, treasure `Slot`s, the outpost, door lists, the "locked, never opens" restroom doors, hide zones. Each 18 m cell is planned with its **own generator seeded by a hash of `(floor seed, column, row, 17)`**, in plans (corridor along x, rotated by quarter turns for the other direction) that carve it into corridors, offices, conference rooms, storage/copy/server rooms, open-plan areas, lobbies and, on floor 1, a coffee shop. After every cell is planned, but *before* any is furnished, `EnsureRestrooms` and `EnsureBreakRoom` convert existing rooms (every floor must have a break room and a Men's/Women's pair by the elevator), `PickRoles` makes executive suites and a server room, `PlaceSafe` puts the floor's safes in rooms (suites first), `MergeHideZones` merges the "hide at a desk" triggers. Because each cell's furnishing resumes the generator where its planning left off, **a floor stays what it was wherever the core rooms did not touch it** — a deliberate property so that adding a rule does not reshuffle every floor.
5. **Build the plan (`BuildInterior`).** Partitions become boxes (doorway headers above the gaps); the carpet (rooms) and tile (corridors, lobby) are **one merged mesh per surface**, with no collider so the NavMesh ignores them; every room gets one painted accent wall; furniture comes from `PropTable` → `OfficeCatalog` prefabs, **measured once into inactive templates and cloned**; one carpet colour per floor from a palette of six, no two floors in a row alike. The whole step is wrapped so that *a failure in furnishing falls back to the empty rooms* and logs "Please report this": a floor must always load.
6. **Scenery** (`BuildScenery`, cosmetic and failure-proof): the windows in the outside walls and the night city beyond them (3.6).
7. **Bake.** One `NavMeshSurface` on the floor root (`collectObjects = Children`, `useGeometry = PhysicsColliders`, agent radius 0.5, `BuildNavMesh()`), built **after furnishing and before doors, the ceiling and the loot**, so the mesh sees every doorway as open and furniture as obstacles.
8. **Doors, outpost extras, people and things.** Sliding doors in every doorway (after the bake, so the NavMesh was made with them open; they start as colliders only when shut); the outpost's one-way window, keypad, alarm lamp and lock; the ceiling and its lights (`BuildAfterHours`, after the bake "because a ceiling is not ground"); then `PlaceLoot`, `PlaceMugs`, `PlaceGuards`, the guard on duty, the outpost's contents, the hallway loudspeakers. Each outpost step is wrapped in `OutpostStep(name, floor, action)` so a failure logs `[Outpost] Could not build …` and the floor still loads.

### 3.3 How every machine gets the same floor

Determinism is the architecture's load-bearing wall, and the code is explicit about the rules (`DEVELOPER_NOTES.md` section 7):

* Floor content uses **`System.Random` only**, never `UnityEngine.Random` (whose state is global and per-machine).
* The generator creates objects **in the same order** on every machine, because `NetIds` are creation-order integers. Cosmetic extras (doors, plates, bubbles, sounds, the city, the carpets) take **no ids** and must not.
* Anything that should not disturb the maze, loot or guards takes a **stream of its own**: the armed-guard plan (`new Random(planSeed × 7919 + floor × 31 + 5)`), the carpet and scenery (they *hash the place*, not the floor's generator), the outposts' contents and every safe and note (`SafeRules.Hash(intelSeed, …)`, where `intelSeed = baseSeed ^ 0x2D5AFE1` online).
* After a build the host publishes a checksum of the id table; a mismatch is logged as `DESYNC` (and the QA tests treat it as a failure).
* The planner's input is built in exactly one place (`FloorShape.PlanFor`), which both the generator and `FloorGenerator.SafeRoomLabel` use — two copies could give two answers — and that is what lets a note on floor 2 name the room of a safe on floor 5 without building floor 5.

### 3.4 Where loot, valuables and guards go

* **Valuables** (`ValuablePlan`, `Valuables`): watches, phones, wallets, laptops on the free tops of desks, tables and counters (`SurfaceKeys`), at most two per surface and spread over as many numbered rooms as possible first, then at most 4 in a cell (`LootPlan.Pick`). **Furniture is never loot.**
* **Treasures** (the stapler, trophy, espresso machine, prototype server, executive safe): `10 + floor` of them on the planner's treasure spots. Because a treasure for two or three needs room to be carried, `LootPlan.RoomForCarryCore` runs a **reachability analysis**: a flood fill (`WalkGrid`: 0.25 m cells, a person's 0.3 m half-width kept clear of furniture, walls and the box itself) from the room's doorways and guard stops, requiring that two carriers can stand on *opposite* sides of the box (three: any two sides) and *reach* those spots; a treasure whose spot fails is **moved** by `TryFindCarrySpot` to the nearest passing spot in its room (a fixed-order 0.25 m grid search, no randomness — every machine finds the same one — and, for a moved treasure, the NavMesh must reach within 2 m of it) or is left out. On 15 measured floors, of 187 treasures for two or three: 58 stand as planned, 89 are moved, 40 are left out (servers 24/81/18, safes 34/8/22).
* **Quota** is capped at 60 % of the value actually placed, so it can always be met.
* **Guards**: `GuardRules.PatrolGuards(floor)` = 3 + floor, +2 from floor 3 (at most 12 patrolling); each gets a route of 3–4 stops sampled from random walkable points in cells at least two doorways from the elevator, **keeping only stops that have a complete NavMesh path to the elevator lobby** (a stop in the pocket behind a rack once left a guard standing in a dead end — found by a loot-reachability test); backup officers `roam`.
* **The outpost** sits in the farthest cell that is neither elevator nor stairwell, with its door facing the first open neighbour.

### 3.5 The Loading Docks (the hub)

A 2 × 1 cell basement built in code: the **vendor's room** with three garage doors on its far wall (two shut, the third rolled up onto the back of an articulated lorry's trailer, a hallway of four slabs, where the dealer stands behind a counter with his stock on shelves; the sale zone is a trigger volume that tracks which loot and which players' packs are inside), a **break room** (the TV that the cinematic is played on, fridge, counters, microwave), an L-shaped **PVP room** with a forklift-sized doorway, and the **dart board** hallway. There are no guards and no loot on the docks, so **no NavMesh is baked** for them. Its look is shared with the lobby's background through `DockDressing`.

### 3.6 Scenery, lighting and the sense of place

* **Windows and the city.** The outside walls of an office floor are real openings (piers, sills, heads, steel frames: one merged mesh). Outside lies a **night city** (`ExteriorCity`, `CityStreets`, `CityBuildings`): roughly 900 towers (870 when last counted) in nine merged meshes in near/middle/far bands, a street grid with cars, a dome of sky with stars and a moon out to 840 m, drawn **unlit** (an emissive Standard material with black albedo, depth-sorted from any side) with **no colliders**, built in about 10 ms and freed with the floor.
* **After hours** (`AfterHours`, pure): where the ceiling panels hang and which are on, by area — the lobby and server rooms always lit, corridors lit or half-lit, most offices dark, a break room often left on — with at least 34 % of the panels on. The panels are meshes; a floor also has a couple of hundred *real* lights (some of them at least 4.6 m apart in a room, forced per-pixel because a huge floor box would otherwise get them as vertex lights), but **`FloorLights` keeps only the few nearest the camera switched on** (`maxActive` = at most 8, fewer on low quality levels; rescanned every 0.25 s within 30 m, 0.4 s fades, a "stickiness" so two equally near lights do not take turns): a pixel light costs time on everything it touches, so this is a rolling window of lights around each machine's own camera, purely local and cosmetic.
* **Signs and numbers**: `RoomNumbers` assigns door numbers that follow the corridors so the layout can be *learned*, `DirectionSigns` hangs signs with arrows built from `DotText` (a dot-matrix font rendered to meshes), `FloorDirectory` maps a room number to its doorways (used by the security computer to lock a room).
* **Glass and door windows**, **the planar mirror** in the car and **the one-way window** of the outpost (a second use of the mirror camera) are cosmetic and guarded the same way as everything else: a failure is a warning and the plain wall comes back.

## 4. Specialised sensory and interface systems

### 4.1 Proximity voice chat and how it reaches the guards

One pipeline serves two purposes: teammates hear each other by distance, and guards hear a loud talker.

**Capture and encoding** (`VoiceChat`, `VoiceCodec`). If Steam is up the microphone is **Steam Voice** (`SteamUser.StartVoiceRecording`, `GetVoice` — compressed Opus, roughly 3–6 KB/s); otherwise a fallback `MicrophoneVoiceInput` reads Unity's `Microphone` at 16 kHz and sends raw 16-bit PCM in 20 ms packets (about 32 KB/s; a fallback and a test path). Modes: open mic (default), push-to-talk (T), off; M toggles mute; the settings are `PlayerPrefs`. A "gate" (RMS 0.012) separates speech from silence, there is a 0.25 s hang-over after the level drops, and **silence is not sent**. Packets are sent as Netcode **named messages** (`be.voice`): `UnreliableSequenced` when ≤ 1000 bytes, fragmented-reliable above. A client sends to the host; the host never trusts the claimed speaker id (it uses the real sender) and drops senders over a token-bucket limit (burst 100, 70/s).

**Relay by distance (host).** `Relay` forwards a packet only to listeners for whom `VoiceRules.ShouldRelay(distance, radios)` is true — within the audible range plus a 4 m margin, or when both players carry a radio (a hook for a planned walkie-talkie item: `VoiceChat.RadioOf`; nobody carries one yet) — and, in a run, only if both players have bodies. In the lobby there are no bodies, so everybody hears everybody.

**Playback** (`VoiceVoice`). Each remote speaker has an `AudioSource` fed by a **ring buffer written straight into the audio stream in `OnAudioFilterRead`**, resampled to the output rate with linear interpolation, with underruns faded rather than clicked and latency capped by dropping the oldest samples. **The engine's own 3D falloff and panning never reach audio written there** (measured on 2026-10-17: identical loudness at 4, 11 and 21 m — "you could hear people across the floor"), so the source is plain 2D and the game applies the distance and the side itself: `VoiceRules.Gain` is 1 up to 4 m, then `(1 − (d−4)/16)²` to 0 at 20 m; `PanFor` gives −1…1 from the listener's right vector (less panning inside 3 m so a voice beside you is not thrown into one ear); `LeftGain`/`RightGain` quieten the far ear by up to 70 %; the mix glides toward its target over ~12 ms so a change is never a click. A packet whose gain is under the audibility threshold is **not even decoded**.

**From voice to AI perception.** On the speaker's own machine, `PumpInput` decodes the packet it just captured to measure its **RMS**, and `FeedGuards` converts that to a level 0–1 with `VoiceNoise.LevelFromRms`: **linear in decibels** from the mic gate (≈ −38 dBFS) up to a shout at **−18 dBFS** (each doubling is +6 dB). `VoiceNoise.RadiusFor` maps the level linearly to a hearing radius of **8 m (just over the gate) to 30 m (a shout)** - a normal speaking voice (about −30 dBFS) carries about 17 m, about as far as a teammate hears it (constants `VoiceNoise.RadiusAtGate` / `RadiusAtShout`; until 2026-10-27 it was 3 m and −14 dBFS, and a normal voice reached only about 8 m) - and between two packets the measured level falls away over a few tenths of a second (`MicRelease`) instead of dropping to 0 at once, and every 0.25 s while above `minLevel` it calls `NoiseBus.Emit(playerPosition, radius, player)`. That is the same bus as footsteps and gunshots: guards compare distance with loudness and, if they hear it, **walk to the position** (`Investigate`, then they see what they see). On a client the emit is forwarded to the host (`RequestNoise`, 8 m sanity check). The HUD tells you: "MIC: talking — guards hear you up to 14 m". There is no speech recognition and no per-word analysis — only loudness — and the guards path to a *position*, which makes the NavMesh pathfinding and the state machine the only consumers.

### 4.2 Audio

* **No middleware.** Sound is Unity's `AudioSource`/`AudioClip` plus a lot of code. `GameAudio` is the one-shot player over a pool of 32 sources (3D with `minDistance` 2.5 m / `maxDistance` 30 m by default, a spatial sound outside earshot is not played at all); `SoundBank` resolves a `SoundId` + variant to a clip, **preferring a real clip assigned in the `AudioCatalog` ScriptableObject** and otherwise **generating a placeholder from maths** on first use and caching it (`ProceduralSound`, `OutpostSound`: doors, keys, radios, keypad beeps, the alarm, safes, crowbars, punches, the ping…, each in a few variants so repeats differ). `SoundId` order is the table of `GeneratedVariants`: new ids are appended at the end.
* **The DSP** (`Dsp`, `SynthRandom`) is plain C# at 32 kHz mono — sine/triangle/PolyBLEP saw and pulse, envelopes with per-sample decay constants, a xorshift generator so the same seed always makes the same sound off the main thread.
* **Gun sounds** are *recordings* (the Free Weapon SFX pack: handgun, assault rifle, shotgun sets) cut by `GunSounds` into shot, reload steps (five sounds each at its own time, scaled to the reload length), dry-fire and draw, with per-gun pitch and silenced variants.
* **Music** (`MusicDirector`, `MusicPlan`, `ProceduralMusic`, `LoungeMusic`): three layers on three looping sources — *lobby* (a long WAV in `Resources`: the owner's loop cut up and rejoined into a 2.5-minute song), *elevator muzak* (generated once on a worker thread), and an **intense track that starts the moment backup is called and lasts until the floor ends**. The intense track is **composed from the run seed and the floor number** (`MusicPlan` chooses key, tempo, progression, instrumentation; `ProceduralMusic.RenderIntense` renders it to a `float[]` on a worker thread when the floor loads), so the whole team hears the same one without any music data crossing the network. The mood is derived from state that is already shared (backup called, in an elevator, loading), not sent.
* **Spatial audio of other players' actions**: a teammate's swing, punch, hit and shot are announced by the host and played at his position, fading with distance.

### 4.3 UI architecture, the crosshair and the "minimap"

**IMGUI, not uGUI.** Every screen is drawn with `OnGUI`: the HUD, the inventory, the vendor's shop, the lobby, the Esc menu, the elevator panel, the outpost screens, the cinematic's picture and subtitles. The choices that make that workable:

* **A design system in code.** `HudTheme` holds the palette and its meanings (money green, quota gold, danger red, "free / ready" green, info blue; per-player colours that match between the HUD badge, the ping markers and the Nav map), `Body/Plate/Pill/Panel/Glass/Bar/Ring` primitives (an ink outline, a drop shadow, a pale "sticker" rim, a two-tone cel fill — **all made from `GUI.DrawTexture` with rounded-corner parameters**, so the HUD ships with no textures), `Text` with a thin outline, and `S` — the screen scale (`Screen.height / 1080`, clamped to 0.75–2) that every size is multiplied by. `HudWidgets` builds the HUD's pieces from it (prompts, notices, ammo panel, reticle, scope, status badge, voice pill), `HudIcons` draws icons from primitives, `HudAnim` gives things their bounce, `MenuKit` the menu widgets (dim, sheet, ribbon, buttons), `KeybindScreen` and `HowToPlayContent` the help pages (the keybinds page only *lists* keys: nothing can be rebound yet).
* **Repaint-only drawing and no per-frame garbage** (section 1.6). Interactive screens (shop, inventory, menus) must see every event and use the same code path.
* **Modal state is a handful of static flags** — `Backpack.UiOpen`, `Vendor.ShopOpen`, `ElevatorPanel.Open`, `EscapeMenu.Open`, `TestMode.PanelOpen`, `OutpostUi.Open` (one enum of exclusive outpost screens, *including the cinematic*). `Crosshair.MenuOpen` is their OR; every input script (gun, melee, grab, doors, camera, pings, voice mute) asks it, `CameraFollow` unlocks the cursor when any is true, and `MenuRegistry.CloseAll` closes them all when a Steam invite is accepted. This is also the root of the 2026-10-21 "clicking GO fires a shot" bug: the panel closed on the click while the button was still down, so the gun saw a held trigger; `TriggerLatch` now latches a button that went down while the gun could not be used until it is released.
* **The crosshair is the one place that decides what the player is pointing at** (`Crosshair.Resolve`): a ray from the camera through the screen centre, started at the *player's own depth* (so a wall between the camera and the player is not "in the way"), run to a few metres past the player's reach; the first wall/desk/guard hit is the occluder; items are aimed at by their bounding boxes grown with distance, doorways by their opening (open or shut), the dealer by a cylinder, interactables by their boxes; `AimMath` (pure) chooses among them and E, Q, doors, the vendor and the reticle's colour all read the same `AimTarget`. The ping reuses the same geometry.
* **The "minimap" is a screen on a computer in the world.** There is no HUD minimap or radar. The map is the **Nav tab of the guard outpost's security computer** (`ComputerScreen.NavMap.cs`, `NavMapRules`): a plan of the floor drawn in IMGUI from the `Layout` (rooms coloured by kind, walls, every door, locked doors with a padlock badge, the elevators and stairs, the loudspeakers) with live icons — numbered round badges in each player's colour, red diamonds for officers, the signed-in player's own position — and **no render texture**: shapes (discs, rings, a triangle, a diamond) are generated once as small signed-distance textures (`MakeShape`) and drawn with `GUI.DrawTexture`. `NavView` (pure) does zoom/pan with the spot under the pointer staying put; `NavMotion` tracks each icon frame to frame and, while it moves (> 0.6 m/s), gives off a slight *ping ring* every 0.9 s and leaves a fading dot trail (the owner's request, with teleports above 12 m/s ignored so an elevator ride is not a streak). Clicking a room opens a card with a LOCK/UNLOCK button that sends a host-validated request. Cost is bounded by drawing only while the screen is open and only primitives.

### 4.4 From the cinematic back to the controls

The **run-start cinematic** ("the Intro", `IntroCinematic`, rules in pure `IntroRules`, 60.1 s) plays every time a run starts. It does **not** swap controllers, scenes or cameras; it *borrows the screen* and *inhibits input*, and returns both by clearing flags.

* **Arming.** `RunSync.OnNetworkSpawn` calls `IntroCinematic.Arm` on every machine of a networked run; an *offline* run (PLAY SOLO, or Play pressed on `Greybox`) has no `RunSync`, so `WatchScenes` arms an offline director when the run scene loads (an early version only played in lobby runs — the owner's bug).
* **Waiting.** The director waits (`LocalReady`) until this machine's docks are built, the local player exists and the floor is 0. In a networked run the host then writes `introStart = ServerTime + 2.5 s` into a `NetworkVariable<double>`; every machine plays *the same seconds* of it by reading `NetworkManager.ServerTime`, however long its own docks took. A machine that arrives late finds `IntroOver` and plays nothing.
* **Playing.** Two extra cameras draw into `RenderTexture`s: the **boss's office** (built far from the map on its own layer with its own lights, filmed into the wall TV's 1024×576 texture, hand-rendered each frame with the office's own ambient light) and a **cutscene camera in the break room** that films the TV and five stand-in workers (the players' own characters in slot order plus a coworker beside a lone player, dressed as Tiny Toon people, in a circle talking, then walking at 1.7 m/s to a row in front of the TV) through a chain of `DockShot`s that ease between poses. The result is drawn by IMGUI **above everything** with letterbox bars and typed-out subtitles (30 characters a second). The real players' bodies stand still in the car, their renderers hidden so nobody is seen twice. The timeline is data (`IntroRules.Beats`, 16 beats) and so is every derived quantity (who talks when, when the workers' heads drop, who speaks the last line — picked from the run seed so every machine agrees).
* **Inhibiting.** `OutpostUi.Show(OutpostUi.Kind.Intro)` is the same switch the lock hack uses: the player's body stands still and every other script that asks `OutpostUi.Open` ignores E, Tab, the mouse and the HUD (the HUD widgets themselves check `IntroCinematic.Playing`).
* **Skipping.** Holding Space for 1 s fills a bar; a filled bar is a **saved vote** (letting go does not withdraw it, the owner's rule). The vote is a host RPC (`RequestIntroHold`); the host counts holders against the *current* party (a player who leaves changes what half is) and sets `introSkipped` when at least half are in (1 of 1, 1 of 2, 2 of 3, 2 of 4, 3 of 5). Offline, one hold skips.
* **Returning control.** `Finish()` → `Cleanup()`: the vendor's roller door that was shut for the scene opens (`OpenBay`), a pending vote is withdrawn, **`OutpostUi.Hide(Kind.Intro)`**, the players' renderers are re-enabled, the stand-in workers are destroyed, the TV goes to standby, both cameras are destroyed and both `RenderTexture`s released. Because the real `CameraFollow`, `WobblyPlayer`, `Backpack` and the HUD were never torn down, they simply start answering again the next frame — there is nothing to hand back. It is off in batch-mode Editor tests (so every scenario runs as before) and the built player's autopilot skips it unless testing it.

## 5. How it is tested, built and worked on

The project is developed by a small human team (the owner, who sets the rules and plays the builds, and a second developer who pushes to the same repository) plus AI agent sessions that work **in scratch copies of the project, verify, and then apply files to the real repository with backups**; the owner commits. `DEVELOPER_NOTES.md` (about 1,640 lines, 630 KB) is the hand-off log of all of it: what exists, what was verified and how, what was *not* verified, the owner's requests quoted verbatim, and the "rules of the house".

**The test pyramid** (all driven from PowerShell scripts in `DevTools/QaScripts`, all run in Unity batch mode):

1. **Pure rule tests** (`NetDevTest.PolicyTest`, one `-executeMethod` call after a compile): about **650 checks** against the Unity-free rule classes and the planner — custody and backup timing, guard sight geometry, the hack, the safes' hashing, the door logic, voice gain/pan, the intro timeline and vote, the loot planner on 15 real floors, music/sound synthesis (the Goertzel algorithm checks a generated clip's spectrum), protocol/limits. They fail the compile step first if the code does not build.
2. **Single-process Play Mode scenarios** (`NetDevHarness` + the partial class `NetDevRunner`: 72 of the 88 files under `Assets/Editor`, about 17,400 of its 19,900 lines): `[InitializeOnLoad]` hooks `playModeStateChanged`; each entry point (`NetDevHarness.Pew`, `.Doors`, `.Outpost`, `.LootQa`, `.Asks1021`, …) stores a mode in `SessionState`, opens the `Boot` or `Greybox` scene and enters Play Mode; on entering, a `NetDevRunner` object runs that mode's **coroutine** — it plays the real game (teleports a player, forces a guard's state, fires the gun, presses the elevator panel, takes a picture from a named camera, checks it is not magenta) and logs `PASS`/`FAIL` lines and exits with a code. About 25 such scenarios make the regression set (about 1,300 checks), run with or without a graphics device (`-nographics`; the picture scenarios need one).
3. **Two-process multiplayer scenarios**: a host Unity and a client Unity run the *same* scenario method with different roles (environment variables) over the loopback, synchronised with **signal files** in `%TEMP%` (`Signal`/`WaitSig`/`ReadSig`) — e.g. the client pings an item, the host checks it arrived with the right id and label, the host pings another, the client checks. They need identical code on both sides, or ids and floors diverge and the failures are false.
4. **The built player tests itself.** `QaAutopilot` (`-be-autopilot -be-out <folder>`, honoured only in the Editor or beside a `be_qa.flag` marker file, so playtesters' builds are inert) plays the offline loop of a *built* exe — menu, solo run, docks, floors 1–6 (looking from the elevator, the guards' car, both ends of the outpost, a piece of loot), the demo-complete docks — takes a picture at every stop and counts magenta pixels (an error or stripped shader), logs errors and exceptions, and records frame-time average / 95th percentile / worst, gen-0 GC count and managed heap. Also two built players over loopback, and the cinematic's tests.
5. **A person's eye.** The notes say plainly which items an agent could not judge ("NOT played by the agent"); the owner plays the builds.

**Test-only affordances in the shipped code** are explicit and fenced: `#if UNITY_EDITOR` hooks (`WobblyPlayer.testMove`, `ArmedGuards.ForceForTests`), static `Test…` fields (`GunController.TestTrigger`, `IntroCinematic.SkipForTests`, `LootScanner.TestHold`), the F1 `TestMode` dev menu (Editor only, off in a networked run), and `Application.isBatchMode` checks (the cinematic does not play in batch tests).

**Build and release.** `DemoBuild` makes a Windows x64 player (Mono or IL2CPP) into `Builds/<name>`; scripts in `DevTools/QaScripts` (`ship.ps1`, `final_build.ps1`, `deliver_build.ps1`) zip a build with `README_SEND.txt`; the protocol string in `NetConst` decides which builds can play together, and the lobby refuses a mismatched client in plain words. A zipped build is about 40 MB.

**Working conventions that explain odd-looking code** (`DEVELOPER_NOTES.md`, section 7): scripts are CRLF; never move a player by writing `transform.position`; floor generation uses `System.Random` only; edit-mode guards (`Application.isPlaying`) around anything that needs the running game; never use `?.`/`??` on `UnityEngine.Object`s (Unity's overloaded null); clear every singleton's `Instance` in `OnDestroy`; no `new GUIStyle` inside `OnGUI`; new cosmetic content must take no network ids. Most `Request*`/`Host*` pairs, rules classes and "(the owner, <date>: "<quote>")" comments exist because the code is the record of the owner's design decisions.

## 6. What is thin, unproven or deliberately left out

* **Never profiled.** The performance work is by construction (non-alloc queries, pooling where it matters, culling, one-per-frame prewarming), not by measurement; the only measured numbers are the autopilot's. Floor generation is a single synchronous call (a stall hidden by the closed elevator, not time-sliced); on a slow machine that stall is longer.
* **Real Steam play across machines is outside the automated tests** — the Steam transport is exercised over loopback IP (Editor/development builds), lobbies and relay connections only by hand with real accounts on real PCs; the notes list "real Steam, real keys" under *not verified*.
* **The tower is only partly exercised.** The demo ends at floor 6 (`TowerRules.DemoLastFloor`); the scenarios and the autopilot cover the docks and floors 1–6 (a few run higher floors by teleport); floors 7–13, the hidden elevator and the boss floor exist in code but are lightly tested.
* **Trust in the client.** Movement is owner-authoritative, and the host's validation is built for friends (reach checks, rate limits, plausibility), not for hostile clients; there is no anti-cheat, no host migration, no reconnect and no joining a run in progress. Events that reach a client *while it is still building a floor* are dropped (the checksum shows the damage).
* **Two-machine scenarios currently failing on the untouched code** (found 2026-10-21, nobody has looked yet): `GunNet` (the client never gets the pew into its pack), `DemoNet`'s client (its check "the clip he bought added eight rounds to the reserve, for its price" fails with reserve 24, cash 420), `OutpostNet` ("the pew lies inside the outpost (0)"). They are either stale tests of the pew's earlier rules or real faults in the networked store/ammunition path.
* **Many numbers are placeholders for the owner to tune** (the notes say so wherever it is true: shares of armed guards, backup timings, prices, spreads), and the words on screen are placeholders the owner rewrites.
* **No key rebinding**, no assembly definitions (one runtime assembly, so every script change recompiles all of it), and a lot of IMGUI (cheap to write and allocation-free as drawn here, but not themeable by designers).

## 7. Four flows end to end

**A player fires the pistol in a five-player run.**
1. `GunController.Update` (shooter's machine): `CanUse()` (no menu, cursor locked, body free) and the `TriggerLatch` say the click counts → `Fire()` → `GunMagazine.TryFire` (rounds, interval) → `Shoot`.
2. The aim point is the camera's ray from the player's depth; the muzzle's line is traced with `Ballistics.Trace`; if the crosshair is on a guard but the muzzle's line is blocked, the camera's line is used.
3. Flash, tracer, shell, sound and a guessed hit sound play at once (`GunFx`, pooled; `GunSounds`); `held.Kick()`.
4. `RunSync.RequestGunShot(origin, direction, guardIdSeen, seed)` → `[Rpc(SendTo.Server)]`.
5. Host `HostGunShot`: sender known? gun equipped? not in custody? muzzle within 4 m? not faster than the gun? → for each pellet (its spread from `seed`) `Ballistics.Trace` again (plus `Forgiven` for the guard in the sights) → `HostPellet` → `GuardAI.BulletHitHost(guardHits)` (damage less shield; stop and radio if not dead; `CheckDown` → drop a clip, drop the key) → `NoiseBus.Emit(muzzle, 45 m)`.
6. Host `PlayerShotRpc(slot, endPoint, result, seed)` to everyone but the shooter, who already showed it; each machine draws the shot from the shooter's hand and plays the hit sound by `result`.
7. Guards' new state/flags reach the clients in the next 15 Hz snapshot; a dropped clip is announced as `SpawnClipRpc(id, …)`.

**The team rides to the next floor.**
1. A player clicks a floor on the wall panel, then GO: `ElevatorPanel` → `LocalPress` → (client) `RequestPanel` → host `HostPress` checks the player is at the panel, not in custody, the destination is allowed by `TowerRules`, and that **everyone is aboard** (`WobblyPlayerRegistry.AllAboard`: every non-busted player inside the car's trigger).
2. `Seal` runs a 2 s countdown ("Doors closing in 2 / 1"); if anyone steps out it is cancelled at once and GO must be clicked again; then the doors close and 2.4 s later `TowerManager.RideTo(level)` → `BeginLevel` → `RunSync.BroadcastLoadLevel(level, cargoIds, resume)`.
3. Every machine: `LoadLevelRpc` (epoch + 1) → `TowerManager.NetLoadLevel` → `LoadFloor` → `BuildFloor` (section 3.1) → `HeistManager.StartFloor` → the host `MarkFloorReady()` + `PublishChecksum()`.
4. Clients stop ignoring state when `vReadyEpoch` equals their epoch; `ChecksumRpc` compares the id tables.

**An officer radios for backup and officers arrive.** `ScanForPlayers` accumulates seen-time → `StartCall` (stop, 2 s) → `TickCall` ends → `HeistManager.CallBackup(guard)`: not jammed? `BackupCalled = true`, `backupClock.Start(interval for the floor)`, `SendOfficers(2, where)` → `FloorGenerator.SpawnReinforcements`: pick the entry doors (guards' car, stairwells) by `OrderEntries`, open them (`GuestDoorOpen`/`EntryDoorMask`, published in the run state), spawn each officer with a loadout from `ArmedGuards.RollFor` and the host announces `SpawnGuardRpc(id, pos, look)` so clients create the same puppet with the same id (his loadout then rides in the snapshot byte) → `Dispatch(target)`; the doors close again 7 s later; the banner is sent by `BroadcastBackupMessage`; `MusicDirector` switches to the floor's intense track on every machine because `BackupCalled` is mirrored state; the clock repeats every 30 s (12 s from floor 12) until the floor ends or the alarm is stood down.

**A purchase.** Player at the counter opens the shop (`E` with the crosshair on the dealer): the shop is local IMGUI, drawn from `Vendor.Catalog` filtered by `OnOffer`; a click → `Vendor.Buy(index)` → (client) `RequestBuy(index)` → host `HostBuy` checks the buyer is in the sale zone → `BuyFor`: on offer now? ammunition for a gun they carry and room in the magazine? not a second gun / second armour? weight fits? `TrySpend(price)` → spawn **one** object on the shelf with a fresh id → `AnnounceStored(id, slot)` → every machine runs `ApplyStored` (the item is switched off and joins that player's pack); or, for ammunition, `AnnounceAmmo` and every machine adds the rounds to that player's gun; the buyer's notice text comes back by `NoticeRpc` to that one client.
